# ADR-0011：CHANGES 后自动返修一次，上限默认 1

- 状态：已接受
- 日期：2026-11-24
- 关联：devlog 0003、ADR-0010

## 背景

门禁收到 `REVIEW: CHANGES` 后只拦截并结束本轮，实现者必须等人类再开一轮才能修。实际使用中，review 意见通常已经足够明确（文件、行号、原因、改法），自动把实现者拉回来修一次能省一轮人工接力。但放任自动重排会让实现者和 reviewer 互相触发，形成死循环和 token 消耗。

## 候选方案

- **A. 不自动返修**：保持现状，最安全，但每次 CHANGES 都要人工再开一轮。
- **B. 无限自动返修**：实现者↔reviewer 自动来回。省人力，但容易死循环、成本不可控。
- **C. 一次性返修 + 上限**：CHANGES 后自动排一次返修，返修后重新盲审；达到上限就回到人工接手。

## 决定

选 C。

- 触发条件：盲审开启；门禁拦截原因是 `changes`；verdict 作者是本轮实际选中的 reviewer（指定或池选），不是实现者本人，且 harness 不同；本轮有 `changedAuthor`（最后一个实际改动工作区的实现者）、该角色仍启用、返修次数未达上限。实现者自己、同 harness、第三方的 CHANGES 都不触发自动返修。
- 返修回合：同一轮、同一任务卡；override 带上 review 原文（截 2000 字）和要求“不要自行提交”。
- 返修后把 `blindReviewQueued` 重置，让返修产生的 diff 自动进入下一次盲审；PASS 则正常收尾/自动提交，CHANGES 且达到上限则按原逻辑拦截并结束。
- 上限：`AC_AUTO_REPAIR_LIMIT`，默认 1；0 关闭自动返修。
- 只处理 `changes`；verify 失败、无 review 结论、自审、同 harness 等拦截不自动返修。

## 后果

- **收益**：常见的“review 指出问题 → 实现者修 → 再 review”可以一轮闭环；上限防止自动死循环。
- **代价**：返修回合读完整上下文（不是盲审），可能受实现者自述影响；review 原文过长时会被截断；实现者如果没改文件，返修不会触发新的盲审，最终仍在门禁处结束。
- **不做**：不做无限返修、不自动返修 verify 失败、不让 reviewer 直接改代码。
