# ADR-0005：工作区隔离用 git worktree，非隔离同目录用执行锁

- 状态：已接受
- 日期：2026-11-19
- 关联：devlog 0003

## 背景

一个房间 = 一个工作目录。两个房间指向同一个仓库时，会同时发生两类破坏：两个 CLI 并发写同一批文件（后写的覆盖先写的），以及各自轮末自动提交到同一分支（提交历史混在一起）。用户的实际用法又经常是「同一个仓库开多个房间」——一个改后端、一个写文档。

## 候选方案

- **A. 只管分支**：每个房间 `git switch` 到自己的分支再跑。分支只隔离提交历史，不隔离工作区；两个房间同时 `switch` 还会互相打断。
- **B. 每个房间默认 worktree**：结构上最干净，但对「只开一个房间」的用户是多出来的目录和合并负担。
- **C. opt-in worktree + 非隔离同目录执行锁**：想要并行就开 worktree（独立 checkout + `ac/<room>` 分支）；不开的用户至少串行执行，不会同时写。

## 决定

选 C。

- 房间可在设置里「创建隔离工作树」：`data/worktrees/<roomId>`，分支 `ac/<roomId 前 8 位>`，从 HEAD 切出；源仓库未提交改动不带入；解除隔离删 worktree、保留分支。
- 非隔离房间按 `resolve(workingDir)` 作为 key 加 ref-count 执行锁；同 key 的其他房间排队，持锁方空闲后唤醒。verify 命令执行期间同样持锁。隔离房间没有 key，永不等待。

## 后果

- **收益**：默认用法不变；共用仓库的用户有明确的并行方案；即使不开 worktree，也不会发生并发文件覆盖。
- **代价**：worktree 里的提交要用户自己合并或推送；解除隔离不会自动合并。执行锁只防并发，不防先后两个房间把改动叠加在同一个工作区——要真正隔离仍需 worktree。
- **不做什么**：默认 worktree、自动 PR、自动 merge。这些假设用户有完整的 git/GitHub 工作流，和「指一个目录就开聊」的产品定位冲突。
