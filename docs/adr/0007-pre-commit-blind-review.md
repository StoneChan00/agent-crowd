# ADR-0007：盲审在轮前自动触发，而不是事后复核

- 状态：已接受
- 日期：2026-11-23
- 关联：devlog 0003、ADR-0006

## 背景

SOP 门禁要求每轮有代码改动的回合都拿到一条 `REVIEW: PASS`，且 reviewer 不能是实现者、不能与实现者同 harness。但普通 review 回合读的是完整群聊：实现者的自述、之前的讨论和甩锅都会影响判断。事后看已提交 diff 虽然干净，但那时门禁已经关掉、自动提交已经发生，发现的问题只能靠下一轮修。

## 候选方案

- **A. 保持现状**：reviewer 读完整上下文，PASS 之后再提交。实现简单，但审查容易被叙述带偏。
- **B. 只在轮次报告里做事后盲审**：只读 diff，干净，但不影响已收尾轮次，只能算咨询。
- **C. 轮前自动盲审**：有改动的回合结束后、门禁收尾前，自动把指定 reviewer 排进同一轮，只给它原始需求 + 当前未提交 diff；它的 verdict 直接参与门禁与自动提交。

## 决定

选 C，同时保留 B 作为已提交轮次的事后复核入口。

- 房间级开关「改动后自动盲审」，开启时必须指定 reviewer。
- 触发条件：回合成功、有代码改动、reviewer 启用且非总结角色、与实现者不同 harness、同一轮只排一次。
- 盲审 prompt 隐藏聊天记录、记忆、交接和技能；只保留人格、原始需求、改动文件与 worktree diff（tracked 走 `git diff HEAD`，untracked 按新文件伪 diff 附加）。
- 盲审回合不读也不写 CLI 会话，不触发超时自动续跑，避免污染正常上下文。
- reviewer 若给出 CHANGES，门禁照常拦截；PASS 则进入 verify 与自动提交。

## 后果

- **收益**：审查基于证据而不是叙述；PASS 仍然可追溯（round_checks 记录 reviewer 和消息）；不需要人工先 @ reviewer。
- **代价**：每轮多一次模型调用；盲审依赖指定 reviewer，且与实现者不同 harness；`blind` 标记只在内存队列里，重启会让排队中的盲审退化成普通回合。事后盲审仍不回滚已收尾轮次。
- **不做什么**：不自动多轮盲审、不做跨模型投票、不把盲审作为绕过门禁的额外通道。
